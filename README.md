**Wazuh Windows Detection Lab**

**📌 Objective**

Simulate four distinct attacker behaviours on a monitored Windows endpoint and validate that Wazuh SIEM generates accurate, actionable alerts — demonstrating the transition from passive log collection to behaviour-based, pattern-driven detection engineering.

**⚔️ Attack Scenarios**

**1 · Failed Logon Attempts — Event ID 4625**

**MITRE: T1110 — Brute Force**

Multiple failed login attempts were generated by entering incorrect passwords against a local Windows account.

PurposeReplicate brute-force or password guessing behaviourResultWazuh ingested all 4625 events — 7 hits captured within a 30-minute window


**2 · Successful Login After Failures — Event ID 4624 + 4625**

**MITRE: T1078 — Valid Accounts**

Multiple failed logins were generated, followed by a correct password entry.

PurposeSimulate account compromise after repeated brute-force attemptsResult20 combined hits captured — forms the basis for a correlation-based compromise alert


**3 · Privilege Escalation — Event ID 4732**

**MITRE: T1098 — Account Manipulation**

A user was added to the local Administrators group via Windows CMD.

cmdnet user testuser Password123 /add

net localgroup Administrators testuser /add

PurposeSimulate an attacker gaining elevated privilegesResultWazuh detected the group membership change — user ABHI added to Administrators (Builtin)


**4 · Audit Log Clearing — Event ID 1102**

**MITRE: T1070.001 — Clear Windows Event Logs**

Windows Security logs were cleared to simulate an attacker wiping forensic evidence.

cmdwevtutil cl Security

PurposeSimulate defence evasion by destroying audit logsResultWazuh captured event 1102 before the logs were erased — evasion attempt detected

**🔧 Detection Engineering**

Custom rules authored in /var/ossec/etc/rules/local_rules.xml on the Wazuh Manager.

Rule 100001 — Brute Force Detection

Triggers when 5 or more failed logon events occur within a 60-second window.

xml<group name="windows,authentication,local,">

  <rule id="100001" level="10" frequency="5" timeframe="60">
    <if_matched_sid>60122</if_matched_sid>
    <description>Multiple failed Windows logons detected - possible brute force attack.</description>
    <group>authentication_failed,bruteforce,windows,</group>
  </rule>

</group>

**Rule 100002 — Successful Login Detection**

Captures real interactive user logins, filtering out SYSTEM and background logon noise.

**📊 Key Findings**

Volume ≠ detection — Windows authentication logs are noisy by design; raw ingestion without filtering creates alert fatigue, not security

Correlation > single events — failed logins alone are weak signals; pairing them with a subsequent success creates a high-confidence compromise indicator

4732 and 1102 are gold — privilege escalation and log clearing have near-zero false-positive rates and should always be high-severity

Centralised logging defeats evasion — agents forward events in real-time; clearing local logs after the fact does nothing to a SIEM that already has the data


**✅ What Worked Well**

 Full detection coverage before and after a log-clearing evasion attempt
